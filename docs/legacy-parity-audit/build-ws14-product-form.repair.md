# WS-14 — Products Form, Variants & Media — repair report

Scope: the files the implementation reported (management API + management SPA). No admin files involved.
Commands run: `php -l` on all four PHP files, `php artisan route:list --path=api/v1/management/products`, a full route-table duplicate-name scan, and read-only SFC/TS syntax parsing of the SPA files with the repo's own `@vue/compiler-sfc` and `typescript`. `php artisan test` / `npm run typecheck` were NOT run (fleet rule).

## Fixes applied

1. `storify-management/src/views/ProductFormView.vue` — `buildPayload()` omitted every optional field whose input was left blank, so the edit form could not clear anything: the Store "None (warehouse-only)" option, Warehouse/Section/Category/Currency/unit "None" options, Discount %, bulk pricing, download limits, cost price and the text attributes (brand/description/tags/colour/size/weight) all silently kept their old database value and the payload's `delete_*_id` lists could not compensate. Those fields are now always appended (`''` when cleared); the API converts empty strings to null (`ConvertEmptyStringsToNull` is active in `bootstrap/app.php`, and every one of these columns is nullable and every rule is `nullable`/`sometimes`), so a cleared input really clears the column. `store_id` keeps its create-time guard (required on create) and is only sent empty on edit. Variant rows were already cleared correctly because `syncVariants()` writes null for absent keys — no change needed there.

2. Documentation-only clarifications in the two files where verified runtime behaviour was undocumented:
   - `storify-api/routes/api/v1/management/ws14-product-form.php` — notes that WS-25's module loads after this one and serves `GET products` with a superset payload.
   - `storify-api/app/Http/Controllers/Api/V1/Management/ProductFormController.php` — same note on `index()`.

## Checklist results

1. **Route → method mapping** — PASS. All nine registrations resolve to existing public methods with matching signatures (`Request` first, route-model params in URI order): `index`, `formOptions`, `show`, `store`, `update`, `updateStatus`, `setPrimaryImage`, `destroyImage`, `destroy`. `route:list --json` shows every URI bound to `ProductFormController@...` except `GET products`, which resolves to `ProductListController@index` (see note A).
2. **Envelope + tenant scoping** — PASS. Every method returns `$this->ok(...)` or `$this->error(...)`; the only other exits are the house `abort(403/404)` authorization guards. Reads are scoped to `business_id` + accessible stores/warehouses (`authorizeProduct`, `accessibleProductQuery`, `assignmentError`), cross-business ids are rejected with 422/403, and the multi-write mutations (`store`, `update`, `destroy`, `setPrimaryImage`, `destroyImage`) run inside `DB::transaction`. Reference tables (currencies, size/weight units) are global by design; categories are business+store scoped; `formOptions` stores/warehouses use `accessibleStores()/accessibleWarehouses()`.
3. **SPA calls ↔ routes ↔ api modules** — PASS. `productFormApi` (options/show/create/update/setPrimaryImage/deleteImage) maps 1:1 to registered routes, including the `_method=PUT` spoof for multipart updates. `ProductsView.vue` uses the shared `productsApi` (`index`/`updateStatus`/`destroy`), all registered. Cross-workstream consumers resolve: `SectionDetailView` (`products.edit` name, `/products/create?warehouse_id&section_id`), `StoreProductsTab` (`?store_id`), and WS-25's screens (`/products/:code/edit`). WS-25's `ProductListOptions`/`ProductDetail` types match this controller's `formOptions()`/detailed `payload()` key-for-key (checked field by field).
4. **Route module hygiene** — PASS with a documented overlap. No prefix/middleware wrapper; only `permission:*` groups, same idiom as every sibling module. New names (`products.form-options`, `products.images.primary`, `products.images.destroy`) are unique. The six CRUD names intentionally re-register the thin `ProductController` routes on the same method+URI — the fleet-wide override idiom used by customers/staff/roles/categories/orders/accounting modules, and WS-25's module explicitly states show/store/update/status/destroy stay with `ProductFormController`. A scripted scan of the complete 1107-route table found no duplicate name mapped to different URIs. See note A for `products.index`.
5. **Router/nav module shapes** — PASS. `src/router/modules/ws14-product-form.ts` default-exports `RouteRecordRaw[]` children of `/` (`products/create`, `products/:code/edit`), no leading slash, `meta.title` + `meta.permission`. Static `products/create` outranks WS-25's `products/:code`, and `/products/:code/edit` is not shadowed (3 segments). `src/nav/modules/ws14-product-form.ts` default-exports `NavGroup[]` (deliberately empty — AppLayout owns the Catalog group; the shape and empty merge were verified).
6. **Imports** — PASS. Every import target exists: `@/api/modules/ws14-product-form`, `@/lib/money`, `@/api/client`, `@/api/endpoints` (`categoriesApi`, `productsApi`, `warehousesApi`, `apiErrorMessage`), `@/stores/auth`, `@/stores/ui`, `@/components/StatusBadge.vue`, `@/components/PaginationBar.vue`; backend imports (`InventoryCostingService`, `ActivityLogger`, `ProductFileService`, models) all exist with the called signatures.
7. **PHP syntax** — PASS (`php -l` clean on controller, route module, migration and test). SPA files additionally parse clean (SFC descriptor, template compile, TS transpile).

Also verified beyond the checklist: the bulk-pricing migration is required (no other migration creates `bulk_quantity`/`bulk_price`) and is `hasColumn`-guarded so it is a no-op on drifted databases; the WS-14 test suite's 17 tests were walked against the implementation (route bindings, validation keys, payload maths, costing sync, activity log, image promotion, warehouse-only mode) and line up; money stays in integer kobo for discount maths; no `vendor` naming anywhere in the reported files.

## Notes (verified, deliberate — no change made)

- **A. `GET products` is served by WS-25, not this workstream.** Both modules register the same method+URI and name; `ws25-products-list.php` loads later (module files load alphabetically), so `route:list` binds the URI to `ProductListController@index`. WS-25 documents the takeover and its row payload is a strict superset of the WS-14 list payload, so consumers (including the WS-14 list test, which only inspects names, and `ProductsView.vue`) are unaffected. The WS-14 registration was left in place on purpose: it matches the fleet's existing same-URI overlap for `GET search` (parent + ws19 + ws34) and keeps the widened, warehouse-only-inclusive list as the fallback if WS-25's module ever changes. The dead-code alternative (deleting the registration and `index()`) was rejected because WS-25's module comment states it replaces "the earlier list handler".
- **B. `ProductsView.vue`** was modified by this workstream and is now unreferenced: vue-router 5.3.1 removes a same-named record when WS-25's module adds `products` (`node_modules/vue-router` `addRoute` → `removeRoute(record.name)`), and WS-25's own comment says the file is deletable. The file is coherent (imports resolve, endpoints exist) and was left untouched by this repair.
- **C. Migration timestamp.** `2026_10_06_000001_add_bulk_pricing_to_products_table.php` shares its timestamp prefix with another workstream's `..._add_delivery_agent_id_to_order_deliveries_table.php`. Laravel orders migrations by filename and the two touch different tables, so both run safely in either order.
