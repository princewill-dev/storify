# mgmt-pos — adversarial verification of `mgmt-pos.md`

**Method:** re-enumerated all 7 Blade files under `resources/views/management/pos/**` and the POS blocks in `stores/{show,settings}.blade.php`, `stores/tabs/{settings,orders}.blade.php`, `components/sidebar.blade.php`, `dashboard.blade.php`, `orders/{index,show}.blade.php`; re-read `Management/{Pos,PosSession,PosSale}Controller.php`, `StoreSettingsController@enablePos`, `Management/DashboardController`, `StoreAnalyticsService`, `PosSession` model, the `AppServiceProvider` sidebar composer and `config/pos.php` (+ git history). New stack: `routes/api/v1/{management,pos}.php`, `EnsureTokenAudience`, `EnsurePosStoreAccess`, `Api/V1/{Pos,Management}` controllers, and the business SPA (`router/index.ts`, `api/endpoints.ts`, `DashboardView`, `OrdersView`, `OrderDetailView`, `StoresView`, `StaffView`, `RolesView`, `layouts/`).

**Verdict:** coverage is structurally complete — every file under `resources/views/management/pos/**` (index, show, sessions/index, sessions/show, terminal, _terminal-body, receipt) and all 10 POS routes in `routes/v1/management.php` (index, show, sessions index/show, open, close, enable, terminal, checkout, receipt) map to an entry, and the expensive status calls re-check out:

- `routes/api/v1/management.php` genuinely has **no `/pos` route**; the only management-side POS artefacts are the read-only `pos_enabled` flags in `GET management/stores*` and the auth `me` payload (also present in the SPA type but rendered nowhere).
- `routes/api/v1/pos.php` really is gated by `token.audience:pos` (`EnsureTokenAudience` rejects tokens without the `pos` ability) and `Pos\SessionController` / `Pos\OrderController@history` really scope to `staff_id = $user->id`; `EnsurePosStoreAccess` only checks business + `accessibleStores()` (it does **not** check `pos_enabled`), so it is a generic store guard despite the name.
- The new `GET management/dashboard` stats block has no `open_pos_sessions` / `active_pos_stores`; the new orders API supports `store_id/status/from/to/q/per_page` and **no `source` filter**, and its payload carries no `pos_session_id`; `OrdersView.vue` contains no `source` reference at all; `StoresView.vue` contains no `pos` reference; `AppLayout.vue` has no POS entry; `storesApi.show` exists but is called by nothing.
- The staff/roles side is as claimed: `SpatiePermissionSeeder` seeds `pos open_session|process_sale|close_session|view_history|void_sale`, `StaffView.vue` posts `pin` + `store_ids` and the new `StaffController` persists `pos_pin`, and `RolesView.vue` renders all permission groups dynamically (so the POS group appears without a literal "pos" string in the file).

**No whole feature is missing from the audit.** The findings below are corrections inside covered entries.

## Corrections

1. **The terminal deep-link the audit leans on is dead in the current legacy source.** `config('pos.link')` is **undefined at HEAD**: `config/pos.php` now returns only `idle_timeout_minutes`, and `git -C storify-api show 4e74a04 -- config/pos.php` shows commit `4e74a04` ("decoupled into core api system") deleted `'link' => env('POS_LINK', 'https://pos.storify.ng')` (and `token_expiry_minutes`). `.env.example:69` still lists `POS_LINK`, but nothing maps it into config, so all six call sites — `pos/index.blade.php:61,80`, `pos/show.blade.php:17`, `pos/receipt.blade.php:6,90`, `stores/show.blade.php:15`, `stores/tabs/settings.blade.php:285`, `components/sidebar.blade.php:198` — render `href=""`. The audit's "deep-links to the standalone POS app (`config('pos.link')`, i.e. `POS_LINK=…`)" describes intent, not executing behaviour. The rebuild must introduce its own POS-app URL setting (e.g. `VITE_POS_URL`).

2. **The in-dashboard terminal is orphaned in legacy — nothing links to `management.pos.terminal`.** Every "Terminal" / "Open Terminal" / "Open POS Portal" affordance points at `config('pos.link')` instead; a grep for `terminal` across `resources/views/management/**` finds no `route('management.pos.terminal')`. This strengthens §5.1's obsolescence judgement: at HEAD the in-dashboard terminal was unreachable from the UI, not merely superseded.

3. **`PosController@terminal` silently auto-creates a session** (lines 84–99): if the caller has no open session for the store, the GET issues `PosSession::create([... 'opening_balance' => 0, 'status' => open])` (platform admins match any staff's session; everyone else only their own). §5.1 never mentions this. If any terminal/launcher flow is rebuilt, decide explicitly whether entering it opens a zero-float session.

4. **Per-store session history (§1.3) has no working pagination.** `PosSessionController@index` paginates 20/page, but `pos/sessions/index.blade.php` (43 lines, no `$sessions->links()` and no `pagination` slot — the `data-table` component supports one) renders no pager, so legacy exposed only the first 20 sessions per store. The audit's "paginated 20/page" should be "first 20 only"; keep pagination as a build requirement.

5. **§5.1's dashboard checkout modal has no `notes` field.** `pos/_terminal-body.blade.php` posts `payment_method`, `amount_tendered`, bank/card extras, `customer_name`, `customer_phone` — nothing else. `PosController@checkout` validates `notes` but the dashboard UI never submits it (the staff terminal at `staff/pos/index.blade.php` is where notes exist). Drop "notes" from the dashboard-variant description, or list it as an unwired field.

6. **§6.1's "`store_ids` on staff create/edit" was not a legacy UI capability.** `staff/create.blade.php` renders Role + POS PIN only; `staff/edit.blade.php` renders the roles modal + POS PIN only; staff/show renders assigned stores read-only. The only assignment UI is the store-settings "assign staff" form (`StoreSettingsController@assignStaff`, `stores/tabs/settings.blade.php:245`). `StaffController@store/@update` accept `store_ids` in validation but no form ever posts them. No parity work is needed — the new `StaffView` checkboxes are a superset — but the legacy description is wrong.

## Notes / boundary items

- **Multiple concurrent open sessions per store are possible** in legacy: the duplicate guard is per-user (`where('staff_id', $user->id)`), not per-store, while owner-close targets the store's single latest open session. A store with two cashiers holding sessions leaves one open after an owner-close; the rebuilt list/close flow should surface all open sessions per store and state which one is being closed.
- Minor UI omitted from §2.3: `stores/show.blade.php:14–16` also renders a top-of-page "Open POS Portal" button when `pos_enabled`, in addition to the POS Terminal card.
- Minor filter nuance in §1.1: the status-tab links (`route('management.pos.index', ['status' => …])`) and "All Sessions" drop any active `store_id` (only the store dropdown preserves `status` via a hidden input). The audit's "both preserved in the querystring" is only half true.
- Cross-domain items verified as already covered elsewhere, not missed here: the POS badge in the orders list/detail and the store orders tab (`stores/tabs/orders.blade.php:41`) are in `mgmt-orders.md` / `mgmt-stores.md`; admin approval of `refund_pending` POS refunds is in `admin-orders-finance.md`; the staff terminal surfaces (`PosSaleController`, `staff/pos/**`, `pos.no-store`, POS PIN verify) belong to the Electron/staff POS app and are correctly out of the business-dashboard scope.
- Verified-correct claims worth not re-litigating: dashboard card metrics (`open_pos_sessions` collection + `active_pos_stores`), sidebar composer data (`$sidebarPosStores`, `$sidebarPosOpenCount`, 15-minute cache), store-show card contents, session `close()` semantics (expected = opening + confirmed cash legs, difference = actual − expected, kobo integers, `session_code` route key), permissions on every POS route, and the `pos` audience/self-scoping limits of the existing POS API.
